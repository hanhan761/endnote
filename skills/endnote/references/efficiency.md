# 实验计算效率与适度并发

本流程用于已经获准执行或编排的实验。目标是减少完成时间、提高单位时间有效结果数，并保持结果正确与任务可识别。只添加提醒、看进度或机器仪表时，不创建新的计算任务。

## 授权目标与资源现场

沿用当前实验明确批准的机器与预算，通过 Yun 登记目标和 probe 确认身份。3090、4090 的资源都可纳入当前实验已授权范围；仅授权其中一台时不自动跨机，网站部署目标也不代表所有实验必须在网站主机计算。
优先用现有调度记录、任务身份与只读采样确认可用 CPU/线程、内存、GPU 型号与可用显存、利用率、温度、磁盘空间和 I/O 等待，以及正在运行的工作负载。看板是快照；启动前重新确认资源。缺少温度或资源数据时标为未知，不用监控心跳证明实验有进展。
不要因 GPU 暂时空闲就复跑原实验；先确认原任务身份和状态。不结束、迁移或挤占他人的任务来腾资源。

## 选择并发

- 独立种子、折次、配置评测或互不共享输出的子任务适合并发。依赖链、同一检查点的续跑、共享可变结果文件必须按依赖执行；给独立任务各自的输出目录和固定标识。
- CPU 任务按可用核数、单任务内存与 I/O 预算安排。控制每个子任务的 BLAS/OpenMP 线程数、数据加载 worker 数与进程数，避免每个任务都占满全机；只调整本次任务可控的执行参数，不修改全局环境。
- GPU 任务先看已有负载和单任务峰值显存、耗时。资源需求未知时，用已有阶段数据或预算内的短采样取得估计；不要同时启动多个未知峰值的重训练。
- 对适合并发、资源已确认的任务，通常先尝试两个独立工作单元，观察吞吐、内存/显存峰值、I/O 和温度，再逐步调整；这是起点，不是固定上限或强制最小值。多卡按设备明确分配；跨已授权机器按各自能力分配独立任务，输入和检查点传输成本也计入总耗时。
- 单卡计算已饱和或显存接近项目预算时，保留单个 GPU 重任务，优先重叠 CPU 预处理、数据加载、后处理或其他独立 CPU 工作。轻量 GPU 工作只有在实测资源容纳且总体吞吐有收益时才共享同卡。
- 给系统和已有任务留资源余量，沿用项目温度、显存、内存、磁盘与运行时限。未知约束先用保守规模；不关闭温控保护、不超频、不改驱动或电源配置，不通过改变算法、数据或超参数冒充调度提速。

并发观察出现 OOM、温控降频、显著 I/O 拥堵、已有任务变慢或总吞吐下降时，先停止扩大并发、把后续任务排队，再按现有项目授权处理自己提交的工作。未经授权不杀原实验或其他工作负载。没有稳定收益时降低后续并发。

## 实施与 endnote 状态

复用原项目现有的批处理、调度器或有界 worker pool；没有必要不新增调度服务或常驻 agent。计划包括任务依赖、设备分配、每任务线程数、最大并发和预算内停止条件；资源充足且任务已授权时，直接落实，不能停在建议。
待资源或前置依赖时上报 queued 并继续心跳；实际执行后上报 started。每个需要独立观察的实验保留自己的任务 ID、真实进度、退出码和最终事件。同一项目名字首段保持一致便于聚类，后续包含种子、折次或轮次以便区分。
既有实验已经在跑时，只读分析并提出后续调度；新增独立工作必须属于原已批准实验范围，不通过新进程重复运行现有任务。
沿用已知邮箱与现有邮件规则，不额外发送并发试运行、自检或每个采样阶段的邮件。效率汇报默认在当前对话；确需邮件时沿用既有任务与已授权通知方式，不新增绑定或调高发信额度。并发排队不触发额外开始邮件，通知限额与计算调度分别处理。
有限恢复的 inspect/plan/execute、互斥锁、固定命令、代次与预算限制保持有效；“效率优先”不授权并行续跑同一原任务、不扩大恢复预算。

## 汇报与验收

先汇报实际结果，再给必要依据：使用的授权机器、实际 CPU/GPU 工作分配、峰值并发和每任务线程数、总耗时/完成数、可读的内存显存峰值、排队原因，以及结束事件是否与真实退出一致。
只有可比的同工作量、同配置基线才计算加速比或吞吐提升；没有基线写“已落实并发，收益尚未量化”。未采样的峰值、温度或进度保持未知。不要把计划并发数、GPU 利用率、HTTP 接收或心跳在线当作效率收益。
